# SPI gap closure implementation plan

Created 2026-10-21 from the [native/SPI gap audit](audits/native-spi-gap-audit.md), under the existing [implementation map](map.md) and [signed-off spec](../wayfinder/technical-spec.md). This is an executable issue/dependency index, not a claim that the gaps are closed. Ticket files in `wayfinder-issues/` are the source of truth for status, assignment, blockers and resolution.

The [member-level coverage baseline](coverage/README.md) now records required inherited APIs, callbacks and transitive payloads, with stable IDs and implementation owners. Its frozen requirements survive removal of native imports.

The audit baseline is 186 production, 122 unit-test and 128 integration-test Java files with noncomment native references. The original allowlist validated 20 production and 21 test files; the named-pool foundation expands it to 21 production and 23 test files. Completion requires full API behavior preservation **and** zero native dependencies/references in the required module boundaries.

## Next work

[Transaction lifecycle and callbacks SPI](../wayfinder-issues/28-transaction-lifecycle-and-callbacks-spi.md) is resolved with all native manager operations/callbacks, ID externalization and explicit unsupported mock behavior. Spring transaction adoption and complete native-free unit coverage remain with their existing owners. The next unblocked, unassigned ticket in ascending order is [SPI ABI compatibility and stamp enforcement](../wayfinder-issues/39-spi-abi-compatibility-and-stamp-enforcement.md). The decomposed PDX parent remains open until all children complete. [Boundary checks](../build-tools/migration-boundary/README.md) continue enforcing the shrinking baseline; a pass is not native-free compliance. Current production native file count remains 182, with unit/integration counts 122/128.

Remaining implementation tickets are open and unassigned. Claim the next eligible ticket before implementation; a ticket is eligible only when every `Blocked by:` ticket is resolved. Comma-separated local IDs in metadata express dependencies, while the links below and in ticket bodies provide their names. Use ascending ticket order among eligible tickets unless the user names another. Do not automatically start additional skills or parallel agents.

## Shared completion requirements

Every linked implementation ticket, including the existing named-pool foundation, must satisfy these requirements:

- Follow the signed-off architecture: typed SPI contracts, native adaptation inside the native driver, injected collaborators, no native unwrap/permanent dual API, no new static mutable state/singletons or reference-count registry. Preserve existing method semantics and ABI rules; new driver operations default to typed unsupported as specified.
- Update stable coverage-matrix rows with native member/type, Spring caller or public exposure, SPI equivalent, provider behavior, tests and owning ticket. Account for inherited APIs, application-supplied callbacks and all reachable event/result/configuration types. An absent method is a missing implementation, not an expected-unsupported feature.
- Native support must delegate real behavior. Mock support must state what it implements locally and reject unavailable operations explicitly. Never accept a required configuration silently, discard an event payload, replace native semantics with an unverified approximation or make runtime tests pass with canned remote results.
- For each changed public consumer group, migrate its callers, Java/annotation/XML wiring, schema contracts, exception translation and affected tests together. A foundational SPI ticket may leave consumers native only when their matrix rows name the downstream cutover owner. Preserve full-source compilation during staging; if the group is too large, create bounded blocking children and leave the parent open until all obligations are complete.
- Add meaningful shared behavior/unsupported tests and native-specific integration tests for network, durability, authentication, serialization or persistence semantics. Record exact native artifacts. Run relevant driver/core/contract and consumer checks plus compilation of affected source sets; keep Spring Test compile coupling visible. Existing scoped pass counts are not proof of full migration.
- Run `verifyMigrationBoundary` during migration and prune resolved entries with `pruneMigrationBoundaryBaseline` before completing their owning ticket. The normal `check` tasks also run this whole-module gate. `verifyNativeFreeBoundary` must pass at final dependency removal. No blanket exclusions, test deletion, baseline expansion or API removal to manufacture compliance. A reviewed scope change must be recorded separately; it cannot be inferred from a difficult-to-migrate method.
- Preserve user changes in Gradle/settings and other work. If required, use the guarded temporary Spring Test init script and session-only escalation without a persistent prefix. Do not commit, publish or merge merely because a ticket is resolved.
- On resolution, append an Answer with source/coverage rows, behavior, commands/results, limitations and any blocking follow-ups; update the map's completed-decision index. Do not close a contract family while required child work remains.

## Remaining boundaries

- This plan implements the existing Spring Data-exposed/used native surface, including transitive public and callback types. It does not silently expand to mirror every unrelated GemFire SDK API. The coverage inventory must resolve ambiguous reachability with evidence.
- Native GemFire globals may pass through inside a driver; adding a driver-owned global registry remains forbidden. Mock independence is not a shared native isolation guarantee.
- The separate Spring Test module's native migration remains out of scope. Its compilation and Spring Data's removal of native helper usage are explicitly owned above.
- Initial supported release selection, official support/EOL documentation and publication/merge scheduling remain release planning. Technical acceptance does not authorize those actions or establish an unverified support policy.
