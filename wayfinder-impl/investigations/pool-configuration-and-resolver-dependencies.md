# Pool configuration and resolver dependencies

Local source/artifact investigation, 2026-10-21. Resolution belongs to [Pool configuration and resolver migration dependencies](../../wayfinder-issues/12-pool-configuration-and-resolver-dependencies.md). No production changes or new runtime test results are part of this investigation.

## Selected boundary

Implement **named driver pool creation and ownership** next: a small typed pool configuration, a driver pool handle, creation/named lookup on an injected connection, and an independent Spring owner/borrower factory. Use ordinary Java/bean XML wiring. Keep the native `PoolResolver` family and its native consumers coherent until their query/function/region dependencies migrate.

A resolver-only return-type change is not a complete slice. Five production consumers use `PoolResolver`: `PoolFactoryBean`, `ClientCacheFactoryBean`, `ClientRegionFactoryBean`, `AbstractClientFunctionTemplate` and `ContinuousQueryListenerContainer`. Several need actual native pool/query/function objects, not just a name. Converting their resolver interface now requires those consumers to move too, or a prohibited native unwrap. The selected foundation does not introduce a second Spring resolver interface or adapt a driver pool back to native `Pool`. Applications use injected `DriverPool` beans and `DriverConnection.getPool(name)` directly; the existing resolver interface will eventually migrate once its consumers can follow.

The next slice deliberately covers endpoints, optional minimum connections, named lookup and destruction. It does not claim to replace all legacy pool tuning, cache default-pool configuration, namespaces or annotation/configurer entry points. Those remain migration work, not permanently supported parallel APIs. No architectural decision needs reopening.

### Native pool/default-cache distinctions

`PoolManager.createFactory/find/getAll` delegate to native `PoolManagerImpl.getPMI()`. `PoolFactoryImpl.create` itself obtains the global distributed system and cache. The public `ClientCache` API has **no instance pool factory or named pool lookup**. The driver must use the native pool API internally; inventing a private independent `PoolManagerImpl` would disconnect pools from native region/query lookup. Spec §5.7(6) explicitly permits native globals to pass through. Do not add any driver-owned static registry, static resolver, cache singleton accessor or reference counting.

`PoolManagerImpl.register`, bytecode offsets 38–64, rejects a duplicate name. Named creation must retain this behavior, not silently reuse. `PoolFactoryImpl.addLocator/addServer` reject mixing endpoint kinds. `PoolManagerImpl.unregister` rejects a pool still attached to regions; `PoolImpl.destroy(boolean)` also has native attachment/durable-specific handling. Record destroy failures; never advertise unconditional successful teardown or emulate native special durable behavior in the mock.

`GemFireCacheImpl.getDefaultPool` calls `determineDefaultPool` when its field is null. That method can select an existing pool, find a compatible pool, return null when there is no selection, or create a pool, including a generated name if `DEFAULT` is already occupied. Thus the cache's **default pool is not necessarily the pool literally named `DEFAULT`**, and asking for it can create native state. Default-pool lookup/configuration is excluded from the next slice rather than being approximated with `getPool("DEFAULT")`.

The Spring default bean name is **`gemfirePool`**, with XML alias `gemfire-pool`; `CacheUtils.DEFAULT_POOL_NAME` is **`DEFAULT`**. [ClientCacheFactoryBean][cache-factory] uses the former when resolving its configuration source. [ClientRegionFactoryBean][region-factory], lines 263–286, filters out the latter so native region creation can choose the cache default. Explicit factory pool name wins over region attributes; non-default names must resolve eagerly through the composed bean/native lookup. These two names are not interchangeable.

## Configuration: what actually reaches native code

[ClientCacheFactoryBean.configurePool][cache-factory], lines 282–332, wraps the supplied/resolved pool with [DelegatingPoolAdapter][delegate] and [DefaultableDelegatingPoolAdapter][defaults]. Scalar precedence is **explicit non-null cache-factory value → supplied/resolved pool getter → factory defaults**. Nonempty explicit endpoint lists take precedence; an empty list does not erase the fallback list. `resolvePool`, lines 348–365, first uses the supplied pool, then named resolution, then dereferences `&<pool-name>` as `PoolFactoryBean` and reads its configuration view. The supplied pool is a configuration source; it is not simply installed as the cache's default handle.

Endpoint selection is conditional: explicit servers, or absence of explicit locators, enables server copying; explicit locators, or absence of copied servers, enables locator copying. Therefore locator-only configuration avoids fallback localhost servers; explicit servers avoid inherited locators; specifying both can reach native mixed-endpoint rejection. With no pool source, [FactoryDefaultsPoolAdapter][factory-defaults] provides localhost:40404 and no locators. A supplied locator-only pool has an empty server list and supplies locators instead. These are Spring rules, not a universal named-pool native default.

[PoolFactoryBean.configure][pool-factory], lines 321–360, applies its concrete defaults and all configured values, then locators followed by servers. It does not choose one kind, or itself invent a localhost endpoint. XML adds localhost:40404 when it sees no endpoint declarations. Programmatic/annotation named pools do not acquire that XML fallback through this factory.

| --- | --- | --- |

| Durability | `keepAlive` used at named pool destruction | Durable ID/timeout and `readyForEvents` belong to cache/distributed-system lifecycle; cache close also has keep-alive. Setting subscription or durable properties alone is not proof of queue retention/readiness. |

Future handling must reject unsupported requests explicitly, not silently accept. |

Full native defaults are in the API snapshot. In particular: free/read/ping timeout 10000ms; socket connect 59000ms; server connection timeout 0; load conditioning 300000ms; idle 120000ms; ping interval 10000ms; retries/statistics -1; subscriptions false, redundancy 0, tracking 900000ms, ack 100ms, timeout multiplier 0; multiuser false. These are **this artifact's** defaults, not SPI constants to freeze for every provider. New optional values should remain unset so the native driver applies its version's defaults.

## Annotation, XML and initialization dependencies

- [AddPoolConfiguration][annotation], lines 83–213: per-name property overrides general pool property, which overrides annotation value; registers native `PoolFactoryBean`. Socket factory uses a bean reference. `AddPoolsConfiguration` loops the same registrar. Endpoint annotation arrays and string forms are appended; nonblank property input replaces that annotation combination. **Exception:** server property fallback at line 270 is literal `"servers"`, not `poolProperty("servers")`, unlike locators. Treat this as an existing inconsistency to resolve explicitly when migrating entry points.
- `PoolConfigurer` is `Configurer<PoolFactoryBean>`. The factory applies XML locator additions, then XML server additions, then user configurers; user configurers can replace/augment earlier endpoint state. Existing pools discovered at bean initialization skip this entirely. [LazyResolvingComposablePoolConfigurer][lazy] delegates to [AbstractLazyResolvingComposableConfigurer][lazy-base]: lazy `getBeansOfType(..., true, false)`, sorted with `OrderComparator`, cached only if nonempty, synchronized application. An injected nonempty list bypasses that lazy discovery. Do not mistake resolver handle caching for configurer-list caching.
- [PoolParser][parser], lines 84–148: scalar property mappings, nested endpoints plus attribute-list configurers, default endpoint only when both forms are absent. It maps keep-alive and subscription timeout multiplier, but does not map socket-factory reference or server-connection-timeout in this method. XML declarations and schema must migrate with the factory, not by changing one return type.
- [ClientRegionPoolBeanFactoryPostProcessor][region-order] adds region `dependsOn` matching a named pool bean. [ClientCachePoolBeanFactoryPostProcessor][cache-order] exists, but **its registration is commented out** in both the parser and `ClientCacheConfiguration`; do not describe it as currently enforcing pool-after-cache ordering. The factory's eager cache lookup is the active workaround. Both registration paths use static `AtomicBoolean` guards, so new code must register infrastructure per bean-definition registry instead of copying process-wide guards.
- [GemFireMockObjectsBeanPostProcessor][test-bpp], lines 155, 213–225: installs a native `PoolFactoryInitializer` returning Spring Test's mock native factory. Its client-cache initializer is similarly native. [GemFireMockObjectsSupport][test-support] keeps static registered pool names and registers mock pools with native internals. These tests are not evidence for the native-free official mock. Spring Test migration stays out of scope, but removing native factory interfaces at final cutover requires addressing its compilation coupling. Its integration configuration also mutates native cache-factory server endpoints.

## Minimum next SPI and Spring slice

Use these names as the implementation target; keep the surface small:

1. Immutable `PoolConfiguration` with explicit server **or** locator endpoint values (host/port), plus optional `minConnections`. Defensively copy endpoint collections; require a nonempty single endpoint kind for this explicit named-creation API. Preserve unset versus zero. Do not store native defaults, resolved DNS state, native callbacks or arbitrary property bags. Minimum connections allows native tests to select zero without claiming that no background networking exists.
2. `DriverConnection.createPool(String, PoolConfiguration)` and `getPool(String)`. Require an open CLIENT connection and a nonblank name; named lookup returns null on absence, propagates errors otherwise. Creation never implicitly borrows/adopts. These methods default to typed `NOT_INTRODUCED` unsupported for old implementations. Do not change existing connect/close/region methods or the ABI stamp policy.
3. `DriverPool`: `getName`, `getServers`, `getLocators`, `getMinConnections`, `isDestroyed`, `destroy()`, with the established typed unsupported defaults. Endpoint getters describe effective configured endpoints, **not online servers**. No Java identity guarantee across lookup wrappers. `destroy()` delegates normal native destruction with no queue-retention request; do not expose keep-alive, query services, statistics, socket callbacks or readiness prematurely. Native runtime errors retain their causes through driver exception translation.
4. Native implementation uses the wrapped cache to enforce live CLIENT access and delegates named pool creation/lookup inside the driver to native `PoolManager`. No preflight find-and-adopt, `PoolManager.close()`, own static state or wrapper cache. Native globals and collisions remain visible across compatible connection wrappers. It cannot promise isolation or exclusivity. A rejected duplicate must leave the existing pool intact.
5. Official mock implements only local configuration records/named lookup/destruction, held per connection. Destroyed pools cease to resolve; connection close destroys its local pool records. It retains configured endpoints/minimum metadata and documents its own default minimum. It never opens sockets or interprets successful pool creation as live connectivity. Existing nonlocal-region/network-search unsupported behavior remains. Query/functions/durable/socket features stay absent or typed unsupported as their operations are introduced. Mock isolation is provider-specific, not a shared promise.
6. Native-free `DriverPoolFactoryBean`: constructor `(DriverConnection, String, PoolConfiguration)` owns the created pool; `(DriverPool)` explicitly borrows. Initialize once, publish only a valid result, clean up a returned owned handle on initialization failure with suppressed cleanup errors, and make shutdown terminal. Unopened/borrowed factories destroy nothing; owner destroys its pool at most once and never its connection. Propagate destruction failure without reporting successful release. Use instance fields and explicit injection, with no native superclass or `BeanFactoryAware` lookup. Spring FactoryBean product must not acquire a second inferred destruction callback.

Connection ownership precedes pool ownership. Wire the pool owner to the connection product so Spring destroys dependents before the connection owner. Later region migration must establish region-before-pool destruction and pass through native attached-region rejection. A borrowed pool's actual owner must outlive its users; the factory cannot enforce this with reference counting.

This foundation creates usable injected pool handles without pulling native queries/functions into Spring. The richer settings table above remains the checklist for a later configuration expansion. Default-pool pre-connect configuration and late lookup semantics must be handled together; supplying a named pool after connection creation does not retroactively configure the default cache pool.

## Verification plan and limits

The implementation ticket must run shared mock/native contracts for explicit named creation, endpoint/minimum metadata, lookup miss/hit, duplicate failure preserving the original, destroy/removal/recreation, closed/wrong-mode failures, and typed defaults on older implementations. Do not assert wrapper identity, exact DNS-normalized host spelling, two-cache isolation or server availability. Use unique pool names, sequential native contexts and explicit owners; use minimum connections zero for no-server fixtures and still clean up all native resources.

Spring tests on both focused classpaths must exercise Java and ordinary XML owner/borrower wiring, a second unusable connection to verify qualification, stable FactoryBean product/type, destroy ordering, context-refresh failure cleanup and a borrowed handle surviving context close. Recording collaborators cover unopened destruction, null/destroyed creation result, creation failure, cleanup failure suppression, terminal access and close-failure behavior without simulating native internals.

Native-only characterization must establish mixed-endpoint rejection, duplicate/global visibility through compatible connections, lookup after destruction, and behavior when a region still uses a pool. A client proxy region can exercise attachment without a functioning server, subject to actual artifact behavior. Default-pool reuse/name selection and keep-alive/network queue behavior are separate native concerns, not shared mock tests. Do not infer successful subscription/durable/authenticated operation from configuration acceptance.

Existing fixtures to consult include the five resolver unit suites, `PoolFactoryBeanUnitTests`, the three adapter suites, `ClientCacheFactoryBeanUnitTests`, `ClientRegionFactoryBeanUnitTests`, function-template/CQ unit suites; pool namespace/already-exists/client-cache-pool/property/configurer/SpEL integration suites; and Spring Test's default-pool-registration and eager-initialization tests. They contain native stubs/global cleanup and cannot simply become the new shared contract.

After implementation, run focused Spring mock/native checks, all driver/core/contract checks and full main/unit/integration-source compilation (including Spring Test compilation). Preserve user Gradle/settings edits; use the guarded `/private/tmp/sdgf-resolver-validation.init.gradle` when needed, `-DgemfireVersion=10.4.+`, and session-only escalation with no persistent prefix for Gradle. Record the resolved artifact again because the selector can advance.

**This investigation ran source/index/document checks and local `javap` inspection only.** It did not execute Gradle, start servers or validate native pool teardown at runtime. The findings about existing gaps come from source/bytecode; the next ticket supplies executable coverage. Full pool/resolver/legacy-factory migration remains incomplete.
