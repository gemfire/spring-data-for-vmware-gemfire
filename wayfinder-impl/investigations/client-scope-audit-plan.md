## Work rules

1. Take one listed batch from an eligible family. Inspect exact members together against pinned native source and current Spring consumers; record a shared rationale only where that evidence applies to every selected row. Constructors, constants, overloads and inherited members must remain visible.
2. Classify straightforward client contracts and server exclusions in batches using exact IDs. Keep existing implementation status independent. Excluding a type by its name, lack of current Spring calls or absence of SPI implementation is insufficient.
3. Record ambiguities as a precise question, source paths already inspected, the competing outcomes and why the answer changes scope or the typed boundary. Add a runtime probe only if source/existing evidence cannot settle it. Stop when that question is answered; do not turn scope review into full adapter implementation or compatibility certification.
4. Each child ends when its fixed IDs are classified, excluded implementation/source mappings are reconciled, necessary retirement is done, and retained work has active implementation/consumer owners. Definition of the required semantics is enough; implementation signatures and full shared/native/mock compatibility remain in existing implementation tickets.
5. Keep unresolved decisions owned by the child until resolved. Remove each classified ID from its pending policy group before adding its final decision; delete empty pending groups. Keep the frozen assignment ledger intact. Task 64 explicitly assigns any new discovery and records why; never silently expand a child.
6. Run coverage generation/check, scope-policy tests and declaration/ownership validation for policy changes. Check the assignment ledger is disjoint, complete and descriptor-stable. Java/build changes also require affected Gradle/boundary checks, run by the user. Documentation-only scope decisions do not require another Gradle run.
