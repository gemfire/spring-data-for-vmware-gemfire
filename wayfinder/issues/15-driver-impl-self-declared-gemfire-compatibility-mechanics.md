## Question

[Driver Impl support matrix and bind-time version check](11-driver-impl-support-matrix-and-bind-time-check.md)'s original bind-time minimum-version-floor check is being superseded by a different model: rather than `driver-core` consulting a centrally-maintained matrix, each Driver Impl **self-declares/self-checks its own compatibility with the GemFire version present at runtime**, and `driver-core` simply asks the Driver Impl that question at `ServiceLoader` bind time (distinct from, and in addition to, the existing SPI-version-range check from [SPI versioning scheme](10-spi-versioning-scheme.md)). The concrete mechanics of this self-check are not yet known. Two things need investigating to make it implementable:

1. **Mechanism shape** — survey how established plugin/driver-style ecosystems let an implementation module self-declare or self-check compatibility with a host runtime version (as opposed to a centrally-maintained compatibility matrix). E.g.: JDBC driver version-reporting APIs, OSGi bundle version ranges, IDE plugin `sinceBuild`/`untilBuild`-style manifest declarations, npm `peerDependencies` / `engines` semantics, or other comparable patterns. For each, note: is compatibility declared statically (a manifest/metadata range compared against a host version string) or checked actively (an API call against the live runtime), and what happens on mismatch (fail to load vs. warn vs. degrade)?
2. **GemFire-side hook** — what does GemFire itself actually expose at runtime for version introspection that a Driver Impl could call to compare "the GemFire version I was built/tested against" vs. "the GemFire version actually present at runtime"? (e.g., a `GemFireVersion`-equivalent API, manifest/build-info metadata, or similar.) Without a concrete answer here, the mechanism from (1) has nothing on the GemFire side to check against.

Do not treat the `udo.kohlmeyer/unified_driver`/GUD branch as a source for this research.

## Answer

### Part 1 — Mechanism shape survey

**JDBC (`java.sql.Driver` / `DatabaseMetaData` / `DriverManager`).** JDBC drivers self-register with `DriverManager` via `ServiceLoader`-style discovery: since JDBC 4.0, a driver JAR ships `META-INF/services/java.sql.Driver` naming its `Driver` implementation, and `DriverManager` loads all such providers at first use. Compatibility is **actively checked, not statically declared**: `DriverManager.getConnection(url, ...)` iterates the loaded drivers and calls each one's `Driver.connect(url, info)` (gated by `acceptsURL(url)`), i.e. it asks each driver "do you handle this?" — a live call, not a manifest lookup. `getMajorVersion()`/`getMinorVersion()` and `DatabaseMetaData.getDriverMajorVersion()`/`getDriverMinorVersion()`/`getDriverVersion()` only *report* the driver's own version for diagnostics/logging; they are not consulted by `DriverManager` to gate loading. On mismatch (no driver accepts the URL, or `connect()` fails) `DriverManager` throws `SQLException: No suitable driver found` — a hard fail, no degraded mode. This is the closest structural analog to the proposed design: an `Impl` module registered via `ServiceLoader` that answers a live "will you work here?" question, with a hard-fail default.

**OSGi (`MANIFEST.MF` `Import-Package`/`Require-Bundle` version ranges).** Compatibility is declared **statically as metadata**: each bundle's manifest states either the version of the packages it exports (`Export-Package: foo;version="2.1.0"`) or an interval range it requires (`Import-Package: foo;version="[2.0,3.0)"`), using OSGi's semantic-versioning interval notation (`[` /`]` inclusive, `(`/`)` exclusive). The **framework resolver** checks these ranges *before/at load time*, without invoking any code in the bundle — pure metadata matching. On mismatch, the bundle simply **fails to resolve/install** (hard fail), though OSGi's resolver will also try alternate providers of the same package if multiple are available, which is a form of soft fallback the fail-fast philosophy here would want to explicitly rule out (single Driver Impl per JVM, no resolver picking among candidates).

**IntelliJ plugin.xml (`since-build`/`until-build`).** Also **static metadata**, but checked by an external host (the plugin verifier / IDE loader / Marketplace), not by live API calls into the plugin. `since-build`/`until-build` must be real IDE build numbers (JetBrains explicitly rejects made-up/wildcard-abused values like `999.*` at verification time) — i.e. the ecosystem enforces that the declared range be *truthful*, not just present. `until-build` is optional and JetBrains recommends omitting it so the plugin stays compatible with all future builds unless something is known to break — the opposite of a "must fail fast" stance, and a useful cautionary data point: open-ended static ranges silently degrade into false compatibility claims over time. On mismatch, the IDE refuses to load the plugin (hard fail), determined entirely at install time from metadata.

**npm `peerDependencies` / `engines`.** Both are **static metadata** in `package.json`, checked by the package manager, not by any live call into the module. Semantics differ sharply by field and by npm version: `engines` is advisory-only by default (produces a warning, `EBADENGINE`) unless the consumer opts into `engine-strict=true` in `.npmrc`, in which case it becomes a hard install failure. `peerDependencies` used to be warn-only (npm 3–6) but since npm v7 are installed/resolved automatically and an unresolvable peer conflict is a hard error. The key nuance: **the same declarative-range mechanism can be configured as either soft-warn or hard-fail** depending on a flag the *host* controls, not the module — which is instructive for a "must fail fast, no soft degradation" design: the failure mode should not be left as a caller-configurable toggle.

**VS Code extension `engines.vscode`.** Static semver range in `package.json`. Notably weaker in practice than the others surveyed: Microsoft's own issue tracker records that a user running a VS Code version below an extension's declared `engines.vscode` floor can still find and install the extension through some install paths — the declaration is honored inconsistently rather than being a hard gate. This is a good negative example: a purely declarative, host-enforced range is only as strict as the host's enforcement code, and enforcement gaps silently reintroduce the "soft degradation" the fail-fast philosophy wants to avoid.

**Summary for this project's philosophy:** the mechanisms split cleanly into (i) *declarative/static* schemes checked by the host before code runs (OSGi, IntelliJ, npm, VS Code) and (ii) *active/live* self-checks where the module itself is asked at bind time (JDBC's `acceptsURL`/`connect`). Static schemes are simple and fast but their strictness depends entirely on host enforcement code being correct and non-optional (VS Code's gap, npm's warn-vs-error flag) — a risk for "fail fast, no soft degradation." The JDBC pattern — the host calls into the candidate implementation and gets a definitive yes/no (or exception) *before* binding — most directly matches both this project's existing `ServiceLoader`-based Driver Impl loading and its fail-fast requirement, because the fail-fast behavior is baked into the contract (throw/return false) rather than depending on an external resolver's configuration.

### Part 2 — GemFire-side hook

Apache Geode (the open-source upstream of VMware/Broadcom GemFire) exposes version introspection at two distinct levels, matching the "built/tested against" vs. "actually running" distinction the question asks about:

- **`org.apache.geode.internal.GemFireVersion`** (geode-core, package `org.apache.geode.internal`) — a static, build-embedded descriptor of *the GemFire jars physically present on the classpath the Driver Impl is running with*. It reads its data from a generated resource, `org/apache/geode/internal/GemFireVersion.properties`, packaged inside `geode-core.jar` at build time, and exposes it via public static methods including `getProductName()`, `getGemFireVersion()`, `getSourceRepository()`, `getSourceRevision()`, `getBuildId()`, `getBuildDate()`, `getBuildPlatform()`, `getBuildJavaVersion()`, `getGemFireJarFileName()`, plus convenience aggregators `asString()`, `asMap()`, and `print(...)`. This is effectively Geode's own manifest-equivalent — resource-embedded build metadata, read with a plain static call, no distributed-system connection required. (Source: `geode-core/src/main/java/org/apache/geode/internal/GemFireVersion.java` in the `apache/geode` GitHub repo.)

- **`org.apache.geode.management.MemberMXBean`** — a JMX management bean exposed per member of a *running* distributed system (reachable once connected/embedded, e.g. via `ManagementService`). It exposes `getVersion()` (full version string: build id, JDK version, product name, release version), `getReleaseVersion()` (version string only), and `getGeodeReleaseVersion()` (the underlying Geode version specifically, useful since commercial GemFire versions and upstream Geode versions can diverge). This is the live, runtime-queryable equivalent — it answers "what version is the distributed system I've actually joined running," as opposed to `GemFireVersion`'s "what jar am I locally built against."

- **Internal ordinal versioning (`org.apache.geode.internal.serialization.KnownVersion`, evolved from the older `org.apache.geode.internal.Version`)** — Geode's own internal mechanism for peer-to-peer wire-protocol compatibility during mixed-version states (e.g. rolling upgrades), used to compare a peer member's version against the local member's and adapt serialization behavior accordingly. It is not a stable/public-facing API, but it is worth citing as prior art *within Geode itself*: Geode already has to solve exactly this "built/tested against X, actual peer is running Y, decide what to do" problem for its own internal protocol, and its answer is a live, ordinal, comparable version object rather than a manifest range.

Practically, a Driver Impl module has two complementary, real hooks: `GemFireVersion.getGemFireVersion()` (or the finer-grained fields) as a **static, local, connection-free check of the classpath's actual GemFire jars** — comparable to reading a manifest — and `MemberMXBean`/`ManagementService`, or equivalent distributed-system-scoped APIs, as a **live check of the distributed system the Driver Impl is about to bind into**, for cases where classpath jars and the actually-running cluster version could differ (e.g. client/server deployments where the client jar version and server cluster version are independent).

### Recommendation

Model the self-check on the JDBC pattern rather than a declarative range scheme: `driver-core` should call a method the Driver Impl itself implements (analogous to `Driver.acceptsURL`) at `ServiceLoader` bind time, and the Driver Impl's implementation of that method should read `GemFireVersion.getGemFireVersion()` (a static, local, zero-dependency check against the classpath jars it's actually co-located with) and return a definitive accept/reject rather than a warning. This keeps the fail-fast contract inside the Impl's own code — not delegated to an external resolver whose strictness can be silently downgraded (as seen with npm's `engine-strict` opt-out and VS Code's inconsistent enforcement) — and avoids reintroducing a centrally-maintained matrix, since the "known-good version(s)" data lives inside each Driver Impl module rather than in `driver-core`. Where a Driver Impl needs to validate against a live cluster it is about to join (rather than just the local jars), `MemberMXBean`/`ManagementService`-style live queries are the available Geode hook for that case, but the classpath-local `GemFireVersion` check should be the primary, always-available gate performed synchronously at bind time, consistent with "must fail fast at bind time, no soft degradation."

### External pattern cross-check

User-supplied external research (a "Startup-Bound Driver-Adapter Pattern with Explicit Capability Negotiation") was evaluated against this ticket's open question and against every already-decided ticket. Two of its ideas were adopted into the sign-off decisions below: (a) the adapter/Impl exposing its declared range as core-inspectable data rather than throwing itself, and (b) the general shape of the core invoking a boundary method and reacting centrally. Two of its ideas were evaluated and **not** adopted because they directly conflict with already-signed-off decisions: SemVer as the compatibility unit (superseded by [ticket 18](18-spi-impl-generation-range-compatibility.md)'s generation-range model) and "log a warning and gracefully degrade" on mismatch (contradicts the standing fail-fast philosophy and [ticket 07](07-unsupported-feature-fail-fast.md)). Tickets 07/08/10/18 are not reopened or altered by this cross-check.

### Sign-off decisions

Signed off by Udo Kohlmeyer, 2026-08-20. Final shape of the Axis B mechanism:

1. **Each Driver Impl self-declares a native-engine range, `[nativeMin, nativeMax]`, expressed in real GemFire product version numbers** (e.g. `10.1.0`–`10.3.x`) — not SemVer, and not the same value space as [ticket 18](18-spi-impl-generation-range-compatibility.md)'s `[implMin, implMax]` generation range. This is a distinct axis: ticket 18's range says which SPI capability generations an Impl exposes; this range says which actual GemFire product versions an Impl has been built/tested to run against.
2. **Bind-time check is JDBC-`acceptsURL`-style, verdict-not-throw.** `driver-core` invokes a method the Driver Impl implements internally; that method reads `GemFireVersion.getGemFireVersion()` off the classpath and compares it against its own declared `[nativeMin, nativeMax]`, returning a boolean/enum verdict — it does not throw itself. `driver-core` is the single place that throws the descriptive, typed exception (from the [exception hierarchy](06-exception-hierarchy.md)) on a negative verdict. This centralizes the fail-fast contract in `driver-core` rather than duplicating exception-construction logic across every Driver Impl.
3. **Sequenced after, and independent from, Axis A.** This check runs after [ticket 18](18-spi-impl-generation-range-compatibility.md)'s SPI-range intersection check at `ServiceLoader` bind time. The two are separate gates checking separate things (SPI capability-generation compatibility vs. actual native-engine compatibility); either can fail fast independently, each with its own descriptive typed exception, and passing one implies nothing about the other.
4. **Live-cluster check (`MemberMXBean`/`ManagementService`) is explicitly deferred, not built for v1.** Only the classpath-local `GemFireVersion` check gates v1 bind time. A live check against the actually-joined distributed system (relevant for client/server deployments where client jar version and server cluster version can diverge) is a candidate for its own future ticket if a real version-skew scenario surfaces in practice — it is not spun up speculatively now.
5. **Declared `[nativeMin, nativeMax]` ranges are governed by the same continuous-CI-enforcement discipline [ticket 18](18-spi-impl-generation-range-compatibility.md) established for Axis A**, extending [ticket 14](14-testing-strategy.md): a Driver Impl's declared native-engine range is only trustworthy if backed by a passing `integrationTest` configuration against every native GemFire version in that declared range, re-verified on an ongoing basis (not just checked once at Driver Impl release) — the same rot failure mode called out in this ticket's Part 1 survey (IntelliJ's `since-build`/`until-build`, npm's `engines`, VS Code's `engines.vscode`) applies equally to a native-engine range left as a point-in-time, unenforced claim.
6. **No change to capability invocation-time fail-fast.** [Tickets 07](07-unsupported-feature-fail-fast.md)/[08](08-capability-enum-evolution-and-removal.md) stand unchanged. This ticket covers only the GemFire-version compatibility gate at bind time, not per-capability dispatch at invocation time — the two remain orthogonal, as originally scoped in [ticket 18](18-spi-impl-generation-range-compatibility.md)'s "explicitly out of scope" section.
